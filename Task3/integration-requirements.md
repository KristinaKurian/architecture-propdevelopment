# Требования к внешней интеграции сервисов «Умный дом»

## 1. Предлагаемая схема взаимодействия

Новые функции доступны пользователю через существующее мобильное приложение PropDevelopment.

Основной контур:

`Mobile App → tenant-core-app → Smart Home Integration Service → API / Integration Gateway → Partner Smart Home Platform → домофон / шлагбаум`

Обратные события:

`Partner Smart Home Platform → API / Integration Gateway → Smart Home Integration Service → tenant-core-app → Mobile App`

Прямые постоянные credentials партнёра в мобильное приложение не передаются.

Для видеосессии домофона допускается отдельный media-flow к платформе партнёра только по короткоживущему session token / signed URL, выданному backend PropDevelopment. Токен должен быть ограничен конкретной сессией, устройством и временем жизни.

## 2. Требования к безопасности

### 2.1. Изоляция данных и авторизация

1. Каждый запрос должен быть привязан как минимум к:
   - `user_id`;
   - `tenant_id / management_company_id`;
   - `residential_complex_id`;
   - `apartment_id` при необходимости;
   - `device_id`;
   - типу операции.
2. Партнёр одной управляющей компании или одного ЖК не должен иметь возможности читать или изменять данные другого tenant/ЖК.
3. Для каждой операции должна выполняться object-level authorization, а не только проверка факта аутентификации.
4. Применяется принцип минимальных привилегий.
5. Права должны быть разделены по scopes, например:
   - `intercom.read`;
   - `intercom.open`;
   - `intercom.manage_access`;
   - `barrier.read`;
   - `barrier.open`;
   - `barrier.manage_plates`.
6. Должен поддерживаться немедленный отзыв доступа пользователя, автомобиля, гостя или партнёра.
7. Все административные операции должны иметь отдельные повышенные privileges.

### 2.2. Биометрические данные и номера автомобилей

1. Биометрические данные лица должны обрабатываться как данные повышенной чувствительности.
2. PropDevelopment не должен хранить raw image лица или biometric template, если это не требуется бизнес-процессом.
3. Предпочтительный вариант — хранение biometric template на стороне платформы партнёра, а в PropDevelopment хранится только внешний идентификатор профиля и состояние регистрации.
4. Регистрация биометрии выполняется только после явного подтверждения пользователя и в соответствии с применимыми требованиями законодательства.
5. Должен существовать процесс удаления биометрического профиля и подтверждение удаления со стороны партнёра.
6. Номер автомобиля передаётся и хранится только в объёме, необходимом для управления доступом.
7. Для номеров автомобилей и биометрии должны быть определены сроки хранения и правила удаления.

### 2.3. Шифрование и секреты

1. Весь внешний трафик — только по HTTPS/TLS 1.2+, предпочтительно TLS 1.3.
2. Для server-to-server соединения PropDevelopment ↔ Partner обязательно mTLS.
3. API keys, client secrets, private keys и сертификаты не должны храниться в исходном коде или конфигурации мобильного приложения.
4. Секреты должны храниться централизованно в secrets manager.
5. Должна поддерживаться регулярная ротация секретов и сертификатов.
6. Чувствительные данные шифруются at rest.
7. Ключи шифрования должны храниться отдельно от данных.

### 2.4. Защита API

1. Все API должны иметь формализованный OpenAPI-контракт.
2. Gateway должен выполнять:
   - проверку authentication/authorization;
   - rate limiting;
   - schema validation;
   - ограничение размера запроса;
   - IP/network policy при необходимости;
   - audit logging.
3. Использовать idempotency key для команд открытия и операций изменения access-list.
4. Каждый запрос должен иметь `correlation_id`.
5. Необходимо защищаться от replay attacks:
   - short-lived tokens;
   - timestamp;
   - nonce или уникальный event/request id.
6. Ошибки API не должны раскрывать внутренние детали реализации.
7. Должно поддерживаться версионирование API.
8. Breaking/security changes должны проходить согласованный процесс изменения контракта.

### 2.5. Webhooks и события

1. Webhook endpoint должен быть доступен только через Integration Gateway.
2. Партнёр должен аутентифицироваться с помощью mTLS.
3. Payload дополнительно должен иметь цифровую подпись/JWS или HMAC-подпись.
4. События должны содержать уникальный `event_id`.
5. Повторная доставка одного события не должна приводить к повторному выполнению бизнес-операции.
6. Должны быть определены retry policy и максимальное количество повторов.
7. Необработанные события должны попадать в DLQ или аналогичный механизм повторной обработки.
8. Логи должны позволять восстановить цепочку `partner event → internal request → user/device`.

## 3. Аутентификация

### 3.1. Пользователь → PropDevelopment

Для мобильного приложения рекомендуется:

- OpenID Connect;
- OAuth 2.1 Authorization Code Flow + PKCE;
- короткоживущий access token;
- refresh token с ротацией;
- MFA для чувствительных операций, если это требуется risk-based политикой.

Мобильное приложение не получает service credentials партнёра.

### 3.2. PropDevelopment → партнёр

Для server-to-server интеграции:

- OAuth 2.0 Client Credentials;
- mTLS для взаимной аутентификации транспортного канала;
- предпочтительно `private_key_jwt` вместо статического shared secret, если партнёр это поддерживает;
- отдельный OAuth client для production и test;
- отдельные credentials для каждого окружения;
- scopes должны ограничивать набор доступных операций.

### 3.3. Авторизация

Авторизация выполняется в двух слоях:

1. **PropDevelopment** проверяет, имеет ли конкретный пользователь право управлять данным ЖК, квартирой, домофоном, шлагбаумом или номером автомобиля.
2. **Партнёрская платформа** повторно проверяет tenant/device scope и не доверяет только переданному `device_id`.

Запрещено строить авторизацию только на идентификаторе объекта из URL/request body.

## 4. Сценарии взаимодействия

### 4.1. Ручное открытие домофона

1. Пользователь нажимает «Открыть дверь» в мобильном приложении.
2. Mobile App вызывает `tenant-core-app`.
3. `tenant-core-app` проверяет пользовательскую сессию.
4. Smart Home Integration Service проверяет право пользователя на конкретный домофон.
5. Команда проходит через Integration Gateway.
6. Gateway получает/использует server-to-server access token и устанавливает mTLS.
7. Partner Platform отправляет команду устройству.
8. Результат возвращается пользователю.
9. Операция записывается в audit log.

### 4.2. Регистрация лица

Предпочтительный вариант:

1. Пользователь инициирует регистрацию в Mobile App.
2. PropDevelopment проверяет право пользователя на объект.
3. Backend создаёт короткоживущую enrollment session на стороне партнёра.
4. Mobile App получает только short-lived enrollment token.
5. Биометрические данные передаются непосредственно в защищённый endpoint/SDK партнёра.
6. Partner Platform формирует biometric template.
7. PropDevelopment получает только `external_biometric_profile_id` и статус регистрации.
8. Raw biometric image и template не сохраняются в системах PropDevelopment.
9. Удаление профиля возможно из мобильного приложения и синхронно выполняется у партнёра.

### 4.3. Автоматическое открытие по лицу

1. Камера домофона получает изображение.
2. Partner Platform/edge-device выполняет распознавание.
3. Партнёр проверяет access policy.
4. При успешной проверке дверь открывается.
5. Событие доступа передаётся в PropDevelopment через защищённый webhook.
6. В PropDevelopment хранится audit event без biometric template.

### 4.4. Добавление номера автомобиля

1. Пользователь вводит номер автомобиля в Mobile App.
2. PropDevelopment проверяет право пользователя управлять парковочным доступом.
3. Smart Home Integration Service создаёт/обновляет access policy.
4. Через Integration Gateway номер передаётся партнёру.
5. Партнёр связывает номер с конкретным ЖК/шлагбаумом и сроком доступа.
6. PropDevelopment получает внешний ID записи и статус синхронизации.

### 4.5. Автоматическое открытие шлагбаума

1. Камера распознаёт номер автомобиля.
2. Partner Platform проверяет whitelist/access policy.
3. При наличии разрешения шлагбаум открывается.
4. Событие доступа отправляется в PropDevelopment через webhook.
5. Событие доступно для аудита и диагностики.

### 4.6. Звонок с домофона и видеосессия

1. Домофон инициирует звонок через Partner Platform.
2. Партнёр отправляет событие вызова в PropDevelopment.
3. Mobile App получает push/event о входящем вызове.
4. Backend создаёт короткоживущую video session.
5. Мобильное приложение подключается к media endpoint партнёра с одноразовым/short-lived токеном.
6. Команда «Открыть» всё равно проходит через backend PropDevelopment и стандартную проверку авторизации.

## 5. Надёжность интеграции

1. Для внешних вызовов задаются connect/read timeout.
2. Retry применяется только для безопасных/идемпотентных операций.
3. Используется circuit breaker для деградации партнёрского API.
4. Недоступность партнёра не должна приводить к недоступности остальных функций мобильного приложения.
5. Статус Smart Home должен отображаться пользователю отдельно.
6. Для команд необходимо различать состояния:
   - `accepted`;
   - `processing`;
   - `succeeded`;
   - `failed`;
   - `unknown`.
7. Для асинхронной синхронизации access policies рекомендуется Outbox/очередь.
8. Должны быть определены SLA/SLO партнёра и процедура эскалации инцидентов.

## 6. Аудит и мониторинг

Необходимо журналировать:

- пользователя, инициировавшего действие;
- tenant/ЖК;
- квартиру при необходимости;
- устройство;
- тип операции;
- время;
- результат;
- partner request/event id;
- correlation id.

Нельзя записывать в application logs:

- biometric templates;
- raw images лица без специального основания;
- access/refresh tokens;
- client secrets;
- приватные ключи.

Необходимо настроить метрики:

- latency партнёрского API;
- error rate;
- timeout rate;
- количество failed webhooks;
- DLQ size;
- число отказов авторизации;
- количество команд открытия;
- состояние интеграции по каждому ЖК.

## 7. Требования к партнёру

Партнёр должен:

1. Поддерживать изоляцию данных разных клиентов/tenant.
2. Предоставить описание модели угроз и мер защиты.
3. Предоставить OpenAPI-спецификацию.
4. Поддерживать OAuth 2.0 и mTLS.
5. Поддерживать ротацию credentials без downtime.
6. Иметь журнал аудита административных действий.
7. Предоставлять механизм удаления пользовательских и биометрических данных.
8. Не использовать данные PropDevelopment в собственных целях без согласованного основания.
9. Уведомлять PropDevelopment об инцидентах безопасности в согласованный срок.
10. Согласовывать изменения API, влияющие на безопасность или совместимость.
11. Предоставлять отдельные test и production окружения.
12. Поддерживать backup/DR для критичных данных и конфигураций.
13. Предоставлять SLA и информацию о плановых работах.

## 8. Ключевые архитектурные решения

В ландшафт предлагается добавить два компонента:

### API / Integration Gateway

Единая точка контроля внешних интеграций:

- authentication;
- authorization policies;
- mTLS;
- rate limiting;
- contract/schema validation;
- security logging;
- webhook protection.

Компонент решает существующую проблему PropDevelopment — отсутствие единых политик безопасности внешних API.

### Smart Home Integration Service

Изолирует бизнес-системы PropDevelopment от vendor-specific API партнёра и отвечает за:

- связь пользователя/квартиры/ЖК с внешними device IDs;
- access policies;
- команды устройств;
- синхронизацию разрешённых автомобильных номеров;
- связь с внешними biometric profile IDs;
- обработку событий партнёра;
- аудит состояния интеграции.

Сервис **не хранит biometric templates**.
